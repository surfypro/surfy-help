# Maintaining the SDK documentation

This section is for **Surfy developers** who evolve the SDK and the public docs.

## Where the documentation lives

| Location | Role | Audience |
|----------|------|----------|
| **`surfy-help/entities/sdk/`** (this folder) | Public integrator docs | Third-party developers |
| **`surfy/docs/surfy-sdk/`** (monolith) | Technical specs, strategy, ADO | Surfy team |
| **`@surfy/surfy-sdk` `*.d.ts`** | Published TypeScript contract | Compiler / IDE |
| **`surfy-sdk-demos`** | Runnable examples + E2E | Integrators + CI |

The **surfy-help** docs must stay aligned with the API **actually exported** (`mountFloor2d` / `mountBuilding3d`, `@surfy/surfy-sdk/react`, `@surfy/surfy-sdk/client`), not with an old “WC only” wording.

## When to update

Update `entities/sdk/` on every change that affects integrators:

- New package surface or entry (`./react`, `./client`)
- New `SurfySdk.*` method or handle signature
- New HTML attribute, event, or error code
- New public React hooks
- Change to HTTP URL or request body

## Consistency checklist (SDK PR)

1. [ ] **`src/surfy-sdk/types/public.ts`** + `index` / `react` / `client` entries
2. [ ] **`docs/surfy-sdk/`** — internal specs aligned AGREED
3. [ ] **`surfy-help/entities/sdk/`** — pages below
4. [ ] **`surfy-sdk-demos`** + E2E
5. [ ] **Semver** — bump `SURFY_SDK_VERSION` if breaking
6. [ ] **Changelog** alpha if visible to integrators

## Writing

- Language: **French** (default locale); EN via i18n.
- Audience: **integrators** — code samples, no internal store/Component jargon.
- Public hooks / API names OK.
- Distinguish **available**, **alpha**, **out of scope** (RN mobile, SSO).
